# Observability stack

All observability K8s resources are built programmatically using Fabric8 manifest builders in `configuration/` subpackages. No raw YAML files remain in the core observability stack. See [`configuration/CLAUDE.md`](../../../src/main/kotlin/com/rustyrazorblade/easydblab/configuration/CLAUDE.md) for detailed builder documentation.

**CNI**: Cilium ENI native routing (no encapsulation; pods get VPC-routable ENI secondary IPs) is the default. `--cni=flannel` at init selects K3s's built-in Flannel overlay instead. A saved state with no recorded CNI predates Cilium and is read as Flannel (`ClusterStateManager.load`). When Cilium is selected, Hubble is enabled for L7 network visibility, Hubble UI is a NodePort on `Constants.Cilium.HUBBLE_UI_NODE_PORT` (31234), and the host add-on collector scrapes the Cilium agent (`localhost:9962`), Hubble (`localhost:9965`), and the operator (port 9963, node-local pod discovery in `kube-system`). `OtelHostCollectorManifestBuilder.buildCniScrapeJobs(cni)` renders those three jobs only for `CniMode.Cilium`; `ObservabilityStackService` reads the CNI from cluster state. The core collector's config does not depend on the CNI. `platform cni` reads the datapath back (`CiliumInspectionService`). `up` marks the install window with Grafana annotations tagged `cilium`, recorded by `CiliumInstallAnnotator` at install time and posted after the stack is up. Before starting K3s on a Cilium cluster, `up` checks every node over SSH for the base AMI's Cilium node fixes (`Constants.Cilium.NODE_FIX_FILES`, via `CiliumNodeImageCheck`) and fails with `Cilium.NodeImageMissingFixes` if any node lacks them.

**Collectors** (run on cluster nodes): two OTel collectors (below), Fluent Bit (journald), Grafana Alloy (eBPF profiling), Beyla (L7 RED metrics), ebpf_exporter (TCP/block I/O/VFS), YACE (CloudWatch), kube-state-metrics (K8s object state, control node, scraped by node-local pod discovery), K3s embedded etcd (`k3s-etcd` job on the host add-on, `localhost:2381`, found by node discovery on the etcd node label), OpenTelemetry Java agent (Cassandra metrics and application logs, over OTLP; the collector tails only the JVM GC log from disk, as `source="cassandra-gc"`), Cilium agent/operator/Hubble scrapes (Cilium clusters only)

**Two OTel collectors** (issue 1092). The **core** (`OtelManifestBuilder`, DaemonSet `otel-collector`) is unprivileged in the pod network: no hostNetwork, no hostPort, rolling update `maxSurge: 1, maxUnavailable: 0`. It is reached through the `otel-collector` Service (`ServiceDns`, `otel-collector.<namespace>.svc`; OTLP 4317/4318, Jaeger 6831/UDP, `internalTrafficPolicy: Local`). It runs `kubelet_stats` (`https://${env:K8S_NODE_IP}:10250`, RBAC `nodes/stats`), the backend, kube-state-metrics, yace and kit scrapes (static kit jobs at `${env:K8S_NODE_IP}:<port>`), and is the only exporter to the backends. Node identity is `K8S_NODE_NAME`/`K8S_NODE_IP` (downward API), never the OS hostname (`NodeScrapeJobs`). Pod logs depend on `PodLogSource`: `NodeFiles` (when `HOST_PATH`) mounts `/var/log/pods` read-only as root with only `DAC_READ_SEARCH`; `None` renders no pod-log pipeline and runs non-root with no host volume. `CollectorResources.podLogSource(capabilities)` picks it for the deploy and the kit sync. The **host add-on** (`OtelHostCollectorManifestBuilder`, DaemonSet `otel-collector-host`, stage "OTel Host Collector" gated on `PRIVILEGED`) is hostNetwork and privileged. It owns the node's OTLP 4317/4318 for host processes (AMI Cassandra agent, profiling reconciler, Fluent Bit, EMR), host metrics (`/hostfs`), host log files, and the Beyla, ebpf_exporter and Cilium localhost scrapes. Every pipeline ends in `otlp_grpc/core` to the Service, and it has no backend exporter, tenant header or memory_limiter. On an update, the stack waits for the core rollout before it applies the add-on (`Stage.rolledOutFirst`). In-cluster producers use the Service: the stress JVM agent and sidecar, the Cassandra sidecar, and the kits through `__OTEL_OTLP_HTTP_ENDPOINT__`/`__OTEL_COLLECTOR_HOST__` (`BuiltinKitCollectorEndpointTest` forbids node IPs). `edl_push_gauges` posts through the API server's service proxy on a short-lived `kubectl proxy`.

**Backend outages** (issue 991): the node collector's exporters hold what they cannot deliver in memory (queue 20000 batches each) and retry without a time limit, so a Mimir restart or outage up to 1 hour loses no sample (Mimir `out_of_order_time_window: 1h`), Loki up to 30 minutes (its out-of-order window), Tempo as long as the queue holds. `prometheus_remote_write` 0.161.0 has `remote_write_queue`, not `sending_queue`; its top-level `timeout` bounds the whole push including retries, so it is `0` (per-request `http.timeout: 30s`); it ignores `max_interval` (fixed 5s retries); `endpoint`/`tls`/`headers` live under `http:`. A collector restart during an outage loses its queue: no `file_storage`, WAL or `memory_limiter`, ever. The Pyroscope Java agent retries without limit and holds 360 snapshots (`Constants.PyroscopeJavaAgent.OUTAGE_FLAGS`); Alloy eBPF has no queue and loses profiles over a ~15s outage (#1206). `CollectorReplayIntegrationTest` proves metrics, logs and traces; `PyroscopeAgentReplayIntegrationTest` proves Java-agent profiles across a 150s Pyroscope outage (every window holds a profile, and the agent log shows no dropped upload beyond one start-race "empty ring" refusal); `JournaldRetryIntegrationTest` proves the Fluent Bit journald sender retries past five failures with no retry delay over 31s (`scheduler.cap: 30` plus the second Fluent Bit adds). Pyroscope 2.3.1 answers 422 (which the agent drops) to every push from SIGTERM to exit, so its `config.yaml` sets both `min_ready_duration` waits (metastore, segment writer) to `0s` and turns usage reporting off; each held shutdown open, and now it exits within seconds. `segment_writer.lifecycler.tokens_file_path` sits on the data volume: without it a restarted segment writer rejoins its ring with no tokens and refuses every push for ~5.5s after start (with them, only a push in the ~20ms between port open and the tokens read is refused). The db-node JFR shipper `edl-profiling-reconcile` keeps a chunk answered 429, or 422 "service is unavailable"/"empty ring", for its next pass; any other 4xx marks it `.rejected`. A full 360-snapshot agent queue measured ~62 MB of heap (0.17 MB a snapshot) on a Cassandra stress JVM only; a synthetic many-stack load measured 5-15 MB a snapshot, so other JVMs can hold more.

**Capability-gated workloads**: an environment declares `NodeCapabilities` (`configuration/NodeCapability.kt`; AWS all, local Docker none). Fluent Bit journald needs `SYSTEMD_JOURNAL` and `PRIVILEGED`; the host add-on, Beyla, ebpf_exporter and the Pyroscope eBPF agent (its own stage, split from the server) need `PRIVILEGED`; pod logs need `HOST_PATH` (one `StageSkipped("Pod logs", HOST_PATH)` when absent); YACE (and its `yace` collector scrape job) needs `CLOUDWATCH`, s3manager (and its `status` section) needs `S3`. A stage whose capability is absent is skipped, not awaited, and reported with `Event.Grafana.StageSkipped`. Where `HOST_PATH` exists, pod logs reach Loki without a journal through the core's `file_log/containers` pipeline.

**Dynamic OTel config**: `OtelManifestBuilder.buildConfigMap()` accepts `List<WorkloadScrapeConfig>` (plus the telemetry redirect and the `PodLogSource`) and injects one Prometheus scrape job per running kit. Kits register by writing `easydblab-metrics-<kit>-<job>` ConfigMaps, one per scrape entry (label: `easydblab.com/workload-metrics=true`); a failed registration fails `start` (`Kit.MetricsRegistrationFailed`). `MetricsRegistryService` creates/deletes these ConfigMaps; `OtelSyncService` reads them all and regenerates the OTel collector ConfigMap. Both are called automatically by `KitRunnerCommand` on successful `start`/`stop`.

**Storage backends** (control node): Mimir 3.2.1 (metrics, port 9009, Prometheus API under `/prometheus`), Loki 3.7.8 (logs, port 3100), Tempo 3.0.3 (traces, port 3200), Pyroscope 2.3.1 (profiles, port 4040). These are Service ports; no pod has a hostPort. In-cluster callers use `ServiceDns(namespace)` (`<name>.<namespace>.svc`, the cluster's install namespace, `default` unless `init --namespace` named one), the db-node reconciler the Alloy relay on `127.0.0.1:4041`, and callers outside the cluster the NodePorts published on owned nodes (`ServicePublishing.NodePorts`): Grafana 31300, Mimir 31009, Loki 31100, Tempo 31200, Tempo OTLP gRPC 31320, Pyroscope 31040. They and Grafana run in the pod network, placed by `ObservabilityHosting` (`configuration/`): the control-node selector and toleration on AWS plus any `init --node-label`, state on `/mnt/db1/<backend>` or a per-workload retained claim, and on AWS the Services published as the NodePorts above for callers outside the pod network. Grafana and the collector reach them by Service DNS (`<backend>.<namespace>.svc`); the CLI still dials the control node until #1090, which owns the grafana Service. Mimir runs no compactor but runs the store-gateway, so every cluster reads the whole shared store for every tenant (`query_store_after: 0`, bucket store synced every minute, a bucket index up to 87600h stale accepted, local blocks kept 15m, blocks the compactor merged away no longer read 10m after their deletion mark, 5m while querying); query sharding is off (`query_sharding_total_shards: 0`), which on one process made dashboard loads several times faster (issue 988); a memcached sidecar in the Mimir pod (`Constants.K8s.MIMIR_MEMCACHED_IMAGE`, 2 GB, `127.0.0.1:11211`) holds the store-gateway's index, chunks and metadata caches and the query-frontend's results cache, and S3 connections stay open for reuse (issue 988); Loki runs `target: all` with its compactor idle. All four write to S3 within minutes as they run: Mimir cuts 1-minute blocks (15s compaction and ship checks, 2m idle compaction), Tempo cuts a block every minute, Loki flushes a chunk at 1 hour (so its per-stream out-of-order window is 30 minutes, and a slow Loki restart does not drop logs) and re-lists its index every minute. `down` saves the tail in two phases (`TeardownFlushService`). Phase A, in order: the annotation mirror (only while logs are pending), then the collector stop (`TelemetrySenders.COLLECTORS`, in order `otel-collector-host` then `otel-collector`, under one deadline: delete each DaemonSet and wait for its pods; a collector already gone counts as stopped). Phase B, at once on a platform-thread pool: the Loki flush (synchronous ingester shutdown answering 204, then scale to 0 and wait for the pod to go), the Mimir flush (ingester shutdown answering 2xx, then scale to 0), the Tempo drain (`TempoTailFlush`: wait for no live traces and a stable created-traces count, then for every local block's `flushed` marker; Tempo is never stopped or restarted), the "profiles need no flush" report, and the annotations backup. Every step runs to completion; a failed mirror fails only logs. `down` only flushes, waits for the flush, and refuses teardown if it did not finish: there is no running check and no WAL, head-compaction or objects-in-S3 check. Any failure stops `down` with nothing torn down and nothing started again — `down` never scales Loki or Mimir up, replaces their pods, or restores the collector (owner decision, 2026-09-26); the failure (`TailFlushFailed`, one `FlushStepFailed` per signal) names each failed signal, its step, and each workload's state. Logs and metrics are recorded in `ClusterState.tailFlush` (per `TailSignal`, completion time only) the moment each flush succeeds, through one writer thread, and `state.json` is written atomically; a re-run skips them and runs the rest again; `up` clears the record. `down --force` lists the unsaved signals before the confirmation prompt. Readers go through `ObservabilityHttp` (per-client SOCKS unless Tailscale, plus the tenant header); `MimirQueryService`, `LokiQueryService` and `LogQl` build on it. Every Grafana annotation is mirrored to Loki (`AnnotationMirror`).

**Account compactor**: an `account-compactor` Deployment on every cluster's control node, redirect clusters included (`configuration/compactor/CompactorManifestBuilder`, deployed as the last `ObservabilityStackService` stage through `services/CompactorStage`). One replica, `Recreate`, pod network, no limits. An init container copies a static `busybox:1.37.0-musl` into the pod; the `lease` container runs the `:compactor-lease` agent jar (`/mnt/db1/compactor/agent/<sha256>.jar`, uploaded by `CompactorAgentInstaller`, so a new jar rolls the pod) on `eclipse-temurin:21-jre`; Mimir's compactor, Loki's compactor and Tempo's backend-scheduler and backend-worker each run under `compactor-gate.sh`, which runs the binary only while `/lease/valid-until` is in the future. Only the holder of the store lease `leases/compactor.json` compacts: the agent renews it every 15s with an S3 conditional write (`If-Match` the last ETag; a create uses `If-None-Match: *`; never retried), and a standby takes over only after seeing one ETag for the 120s TTL on its own monotonic clock. A holder that cannot renew for 60s stops its compactors (SIGTERM, then SIGKILL after 20s), so it stops at most 81s after its last renewal (`LeaseTiming` enforces this). Scratch is `/mnt/db1/compactor/{mimir,loki,tempo}`, wiped on acquire. The compactors read the cluster's `mimir.yaml` and `loki.yaml` plus `compactor/tempo-backend.yaml`; compaction on, retention and every other deletion path off. They use the instance role. `observability compactor status` prints the lease (holder, sequence, renewal time, age) read in the bucket's region, outside a workspace; there is no start or stop.

**Tenant datasources**: `up` and `grafana update-config` list the tenant directories under `mimir/` (`TenantDirectory`) and build Grafana's datasources with `GrafanaDatasourceSet.build(TenantSet, BackendUrls)`: the stable `mimir`/`loki`/`tempo`/`pyroscope` UIDs on the cluster's own tenant, plus `<signal>-<tenant>` and `<signal>--all` (tenants joined with `|`) for metrics, logs and traces; cross links stay within one tenant view; profiles keep one datasource.

**Tenant pickers**: every core and kit dashboard names `mimir`, `loki` and `tempo` only through its pickers, `metrics_datasource`, `logs_datasource` and `traces_datasource`, and every `/d/` link carries the pickers and selected clusters its dashboard declares (`DashboardDatasourceVariablesTest`). The files store no defaults; one install-time pass, `DashboardDefaults`, sets the pickers to the stable uids, `cluster`, `baseline_cluster` and `candidate_cluster` to the current cluster, and the `doc_tenant` options, on every install path (core tree, kit `start`, `grafana install`). The Tests dashboard (`infrastructure/tests.json`) lists every test of a tenant; the three comparison dashboards compare two runs of any lengths in overlay, side-by-side and summary rows. See [`dashboards/CLAUDE.md`](../../../dashboards/CLAUDE.md).

**Observability store and tenant**: every cluster has a tenant (`init --tenant`, default `default`, `InitConfig.tenant`, read with `ClusterState.tenant()`). All observability data lands in the account bucket, laid out by `ObservabilityStore` (`configuration/`): each backend's root sits at the top level, named for the tool — Mimir's blocks at `mimir/`, Loki's at `loki/` (index under `loki/index/`), Tempo's at `tempo/` and Pyroscope's at `pyroscope/` (all native multi-tenancy — they make the tenant directories), and annotation backups at `grafana/annotations/<tenant>/<yyyyMMdd-HHmmss>_<name>-<clusterId>.json` (`SnapshotName`). Each test's documents live at `reports/<tenant>/<name>-<id>/` (`ObservabilityStore.documentsRoot`): `report upload FILE...` stores markdown files there with an HTML copy each and rebuilds `index.html` (`services/documents/DocumentService`), with the operator's credentials, so it works after `down`; `up` rebuilds the index, which says "No documents yet" for a new test. The tenant is published in the `cluster-config` ConfigMap (`tenant`, next to `namespace`); every writer and reader sends it in `X-Scope-OrgID`, and every stable Grafana datasource sends it on every query. Nothing deletes observability data: `down` sets no S3 lifecycle rule, the cluster IAM role is denied `s3:DeleteObject` and `s3:DeleteObjectVersion` under `grafana/` and `reports/` (the compacted roots are left out because the lease-holding account compactor runs with that role, and `pyroscope/` because its v2 compaction removes the segments it merged; compaction is not deletion), the bucket policy denies those deletes under `mimir/`, `loki/` and `tempo/` to the EMR roles, Mimir on a cluster runs no compactor, Loki's compactor is idle with retention and deletion off, the account compactor merges with retention off and removes only sources it merged, Tempo runs with compaction (and so retention) off and `block_retention: 876000h` as a second guard, Pyroscope v2 with retention cleanup off, and the JFR shipper never deletes an unshipped or rejected chunk (it stops recording at its byte bound instead). The observability stack writes nothing to the per-cluster data bucket.

**Restarts by config hash**: `ObservabilityStackService.deploy()` never force-restarts workloads. `ConfigHashAnnotator` stamps each workload's pod template with a hash of the rendered pod template (minus the hash annotation, keys sorted) and of the ConfigMaps it reads (including `cluster-config`), so Kubernetes rolls exactly the workloads whose template or configuration changed, and `ConfigChangeReport` reports "unchanged" only when Kubernetes will not roll the workload.

**Grafana services**: `services/GrafanaDeployService` creates the datasources, renders each core dashboard into its own ConfigMap (labelled `easydblab.com/grafana-dashboard=core`), applies them before the Grafana K8s resources and then prunes the labelled maps it did not render; `services/GrafanaClient` talks to the running Grafana (dashboard install, folders, annotations) and is the `GrafanaAnnotationSource` of the `down` annotation mirror. In the Grafana pod an nginx front (`GrafanaFront`) holds Grafana's port 3000: it sends `GET`/`HEAD` under `/reports/` to an `aws-sigv4-proxy` on `127.0.0.1:3081` that signs for the account bucket's region (`services/aws/BucketRegion`), refuses any other method there, and sends every other path (websockets included) to Grafana, which listens on `127.0.0.1:3001` only; the documents iframe URL is the relative `/reports/...`; Grafana runs with `disable_sanitize_html` so a Text panel can hold the documents iframe.

**Grafana** (Service port 3000, NodePort 31300): Two dashboard sources:
- **Kit dashboards**: JSON files in `src/main/resources/.../kits/<name>/dashboards/`. `KitRunnerCommand` auto-installs them into a Grafana folder named after the kit after a successful `start`. Adding a JSON file is all that's required, unless the kit declares a `dashboards:` list in `kit.yaml` (postgres does, to install each extension's dashboard only in that extension's instance) — then the file must be listed there too.
- **Core dashboards**: JSON files in the top-level `dashboards/<folder>/` tree, one subdirectory per Grafana folder; adding a dashboard is dropping a JSON file into a folder directory, and the mechanism that gets the tree to Grafana is described once, in [`dashboards/CLAUDE.md`](../../../dashboards/CLAUDE.md). **Do NOT add kit dashboards here** — they belong with their kit.


Two commands deploy a dashboard, and they read from different places:

- `grafana install <path> --folder=<name>` deploys **one** dashboard from the path handed to it (`GrafanaInstall` reads `File(dashboardPath)`), after the same install-time pass `up` applies (`DashboardDefaults`, from the workspace cluster state). It needs no `installDist`. It updates the existing dashboard in place **only** if the JSON carries a top-level `uid`; without one, Grafana creates a duplicate on every run.
- `grafana update-config` re-renders the whole tree from `build/resources/main/`, so an edit that skips `./gradlew installDist` silently redeploys the previous build's copy and still reports success.

See [`dashboards/CLAUDE.md`](../../../dashboards/CLAUDE.md) for datasource UIDs, label conventions, spanmetrics metric names, and the correct pattern for cross-dashboard dataLinks (panes= URL format, TraceQL query strings).

**CLI Tool Instrumentation**: The CLI tool uses the OpenTelemetry Java Agent for automatic instrumentation of AWS SDK calls, HTTP clients, JDBC operations, and JVM metrics. No manual instrumentation exists in the Kotlin code. See `docs/reference/opentelemetry.md`.

**CLI commands**: `grafana update-config`, `grafana annotate`, `grafana backup`, `logs query`, `metrics stream`, `metrics list`

All builder paths are relative to `src/main/kotlin/com/rustyrazorblade/easydblab/`. Config resources are at corresponding paths under `src/main/resources/com/rustyrazorblade/easydblab/`.
